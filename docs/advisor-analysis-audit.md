# Advisor: item analysis answered with a greeting

Date: 2026-11-05. After the prompt-isolation build and a fresh conversation, S22 QA reported `Hello` -> `Greetings`, followed by selecting `T4_BAG`. The app displayed `Analyzing Adept's Bag...`; the generated result was `Hello.`. This is a failed item analysis, not a successful result because generation finished.

A subsequent device counter-test reset the conversation and selected the bag as its first request. The answer was `What do you think?`, matching the last English sentence of the analysis prompt rather than analyzing it. Prior Hello history therefore cannot be the sole explanation. This remains a generated-output failure; no claim is made about the model's internal reasoning or whether it is copying input.

## What the app actually sends

- `handleItemSelect` in `screens/AdvisorScreen.tsx` awaits `fetchMarketContext`, builds the analysis prompt, then calls `sendToLLM(prompt, displayLabel, ...)`. The short `Analyzing...` label is only UI transcript text. `LLM.sendMessage` receives the first argument, the full prompt.
- `fetchMarketContext` in `lib/advisor.ts` requests current prices, seven-day history and thirty-day history through `lib/api.ts`. Those functions filter item, server URL, city and quality. An HTTP failure rejects the context and the screen alerts without starting generation. Empty arrays produce explicit `No data` / insufficient-data text, not a replacement greeting. The app may reuse its 30-minute API cache; this investigation did not capture the original S22 response payload or determine its contents.
- The analysis starts with `AI_DECISION_INPUT`, supplies the item name, format, fees, price observations, trend and precomputed flip. The marker is ordinary prompt text, not an enforced native task type or output schema.
- Selecting an item does not reset native conversation. Earlier `Hello` / `Greetings` remains in the same native conversation even though it is absent from the new prompt string. This is a plausible influence, not a demonstrated root cause. The eight-field, multi-section analysis asks considerably more of the model than the greeting.
- `lib/llm.ts` and `lib/litert.ts` forward the message unchanged on Android. Native `sendMessage` passes `userMessage` directly to `Conversation.sendMessageAsync`. The installed 0.17 AAR wraps each call as a new user message with a fresh JNI callback. UI accumulation starts empty and events are filtered by request and stream identity. No application-level response cache or automatic greeting substitution was found.

## Device evidence and its limits

Read-only logcat from the active QA process 30144 records CPU text-only startup and `Engine ready: Qwen3.5-0.8B-VL_int8.litertlm, backend=cpu, vision=false, tools=5` at 10:08:24.577 device time. That establishes the selected backend, not prompt ingestion or output quality. Current logs do not record input hashes/lengths, API row counts, generated text or successful tool executions. Absence of an error/tool log cannot establish that no tool was attempted.

The first 128 KiB of the installed model was read without changing the phone. Its embedded 1,121-byte Jinja template begins at byte offset 16,549 and handles user/assistant/model/system messages, text and image content. It contains no `tools`, `tool_calls` or tool-role serialization. This is the exact vision artifact configured in the registry, SHA-256 `e3360b658c929ff35ab740a21f5e4b688096a72e351b8d347e26ccda314121b7`, pinned to [revision 10243c0](https://huggingface.co/litert-community/Qwen3.5-0.8B/tree/10243c0a01d24e6b122a0e814f8c4d984c9c92d6). This read did not rehash the full 1.3 GB file; the prior completed download's integrity verification is separate evidence.

Independent template rendering with Jinja2 confirms that supplying a `get_prices` tool schema changes no rendered character. A string-content tool-role message is omitted, while list-content tool output lacks role delimiters. A normal Hello -> Greetings -> item-analysis sequence does include the new item request in the correct order. AAR bytecode shows tool descriptions passed separately to JNI, not appended to the system prompt by the JVM wrapper. This demonstrates missing tool support in the bundled template, but does not trace all native runtime processing or prove it caused the greeting response. The item-selection path already provides observations and does not require model-initiated tools.

## Verification and next discriminating checks

New tests execute the actual API/context/prompt functions with simulated HTTP and the screen's extracted production callbacks. They establish filtered item data, explicit empty/error behavior, and Hello -> item sending the analysis rather than the UI label or previous response. Late greeting callbacks cannot overwrite the analysis. If the current mocked model returns `Hello.`, the screen preserves that actual result rather than fabricating an analysis. These are transport/control tests, not inference or full React Native integration tests.

The cause of the off-topic generated answer remains unresolved. Possible contributors include native multi-turn state, the bundled model/runtime/backend combination, and model failure on the longer instructions. There is no evidence yet that simply rewriting another prompt repairs it.

1. The reset -> item counter-test above is complete and still failed. Next verify exact prompt transport with the diagnostic build before changing prompt structure again.
2. Debug APKs now expose a native `debugInference` constant. JS hashes the message asynchronously with SHA-256 without delaying/retrying inference; the native entry hashes the same string immediately before `sendMessageAsync`. Match `request`, UTF-16 `chars`, `analysis`, `image` and UTF-8 `sha256` between `stage=js` and `stage=native`. JS/native logs may arrive in either order. Terminal callback logs report fragment/character counts, not token counts or output text. Hashes are debugging fingerprints, not proof of anonymization, and these new logs are disabled outside debug builds. No full question, image path, output or tool payload is included. Native traces establish entry into the SDK, not correct consumption of every token by JNI.
3. `toolCalling` is now false for this exact Qwen3.5 artifact; Gemma flags, CPU/automatic backend choices, vision and app-side API data fetching remain unchanged. This removes unverified model-initiated native tools (search/prices/history/routes/time) for Qwen; the existing item selector and app market-query fetch paths still supply data themselves. Initialize the model again to apply it: resetting an already-running conversation retains its `currentSupportsTools` value. Require `tools=0` in the new ready log. This metadata correction is not claimed to repair the bad answer.
4. If the task still fails in a fresh native conversation with confirmed input, assess a simpler controlled prompt or a different validated model/runtime. Preserve the same fixture and compare quality, memory, latency and repeated-turn behavior. Do not automatically retry generated analyses or substitute local generic prose.
